# 文本规范化提示词（CG-OCR-WF · 节点 ①「大模型」）

> **用途**：把后端传来的纯文本对话整理成结构化消息数组
> **放置位置**：工作流 `CG-OCR-WF` → 节点「大模型」
> **模型**：Qwen3.7-Plus（纯文本）
> **输入变量**：`{{#<开始节点ID>.chat_text#}}`（paragraph）

---

## 提示词全文

```
你是聊天记录整理器。输入是一段手机聊天记录的纯文本。
把它整理成 JSON 数组，每条消息一个对象：
[{"i":1,"type":"text|emoji|sticker|file|transfer|system_time","speaker":"me|them|unknown","text":"原话","name":"","size":""}]

规则：
1. 若文本带"我/对方/昵称:"等前缀，据此判断 speaker；无法判断填 unknown，不要猜。
2. text 类型：逐字保留原话，不改写、不总结、不润色。
3. 形如 [文件] 文件名 大小 的条目，type=file，**text 留空**，文件名填进 name，大小填进 size。
4. 形如 转账/金额 的条目，type=transfer，speaker 填 unknown。
5. 时间戳单独作为 type=system_time。
6. 只输出 JSON 数组，不要任何解释。
7. 输入为空或无法理解时，只输出 {"error":"NO_TEXT"}。待整理的聊天记录如下：
{{#1794919039684.chat_text#}}
```

> `{{#...#}}` 里的节点 ID 需替换为你自己工作流的开始节点 ID。

---

## 它为什么单独存在

**它不判断，只做结构化。**

后面两个节点都依赖这个结构：

| 下游 | 依赖什么 |
|---|---|
| 代码节点（规则） | 按 `speaker` 判断"谁提出了要求" |
| 研判节点 | 按 `type` 区分"是文字还是文件还是转账" |

**为什么不合并进研判节点**：试过。同一段对话两次输出的格式不一致，前端解析会失败；
拆开之后每个节点只做一件事，输出稳定，而且**每一层都能单独验证**——转录错了看转录，规则漏了看规则。

---

## 与视觉转录的关系

图片模式下，后端会把视觉转录的 JSON **原样**作为 `chat_text` 传进来，本节点相当于再规范化一次。

有点重复（约多花 3–5 秒），但无害——规则里写明"逐字保留原话"，等于把已结构化的数据又过了一遍。
